VPS-28 фиксирует custody закрытого Stage 2 на указанном в задании 72b02da9/0037.

## Что происходит в исходниках

| Ситуация | Результат в обеих ревизиях |
| --- | --- |
| Только явная запись на бесплатный курс и отметка «Начат», либо историческая неявная FREE-запись | Запись/начало хранятся в free_course_enrollments/course_learning_starts. Эти таблицы входят в удаление, а схема квалифицирована обоими локальными fingerprint. Сами эти записи не вызывают финансовый отказ. |
| Курс перевели из FREE в PAID, сохранив имеющуюся FREE-запись | Сохранённый доступ следует из FREE-записи, без создания заказа или course_entitlements этим переходом. Если владелец аккаунта также покупал курс или имеет другую финансовую связь, применяется следующая строка. |
| Есть запись в orders, refund_requests или course_entitlements с customer_id целевого субъекта | ERASURE_FINANCIAL_REVIEW_REQUIRED. Проверка выполняется по существованию строки, без фильтра по состоянию, сумме, каналу, наличию чека или действительности права. Сюда попадают оформленный неоплаченный/отменённый заказ, оплаченный, возвращённый, ручной FX-MANUAL и отозванное право. Котировка без заказа сама по себе в этот набор не входит. |
| Только распознанная аудиторская связь | ERASURE_AUDIT_REVIEW_REQUIRED. Источники — audit_log, control_room_audit_log и ownerLegalEvidenceMentions. В main для customer.id поле actor в audit_log сравнивается целиком, кандидат дополнительно ловит вхождение ID в actor (например customer с префиксом). Прочие поля используют точное совпадение или поиск в JSON по конкретному запросу. Эти проверки не доказывают отсутствие упоминаний во всех журналах. |
| Финансы и распознанная аудиторская связь у того же customer | Финансовый отказ срабатывает раньше аудиторской проверки для этой записи. В утверждаемом плане проверить обе связи. |
| Несогласованная привязка HMAC к аккаунту/email, неизвестная схема, непройденный FK-контроль или иной отказ | Отдельный технический отказ. Это основание для сверки, юридическую причину удержания определяет оператор. |

См. commerce-v2/src/free-enrollment.ts, playback-access.ts, entitlements.ts, erasure-restore.ts и pd-retention.ts
в каждой ревизии. В кандидате меняется вход через общий аккаунт, добавляются MY OTP, обмены и LMS-сессии.
Native-оплаты, возвраты и фискальные события связаны с заказом, строкой или возвратом по FK (0039).
Отдельная проверка nativeErasureAdmission в кандидате смотрит незавершённые оплаты, возвраты и фискальные
события по этой связи. Она тоже возвращает ERASURE_FINANCIAL_REVIEW_REQUIRED для незавершённых состояний,
включая ожидающий оказания расчёт LAB, а после расчёта разрешает только очистку запечатанных конвертов;
финансовые строки подлежат сохранению. На этом SHA проверка вызывается тестами, в erasure-owner/runtime она
не подключена. Её успешный результат не снимает общий отказ erasure-restore по наличию заказа, возврата или
права. У кандидата **частичный исполнитель отсутствует**, как и у main.
При отказе транзакция полного удаления/восстановления откатывается целиком, включая подавление в этой транзакции.
На owner-пути публикация долговечного события происходит до apply (erasure-runtime.ts, erasure-custody.ts).
Поэтому отказ транзакции не означает, что внешнее состояние осталось прежним, и owner CLI нельзя использовать
для безопасного пробного запуска.

## Сохранение доказательств и исполнения после частичного удаления

| Категория | Минимум и контроль до одобрения плана |
| --- | --- |
| Активное право LMS | Сохранить проверяемую связь customer → оплаченная строка → действующее право и путь аутентификации/восстановления. resolvePlaybackAccess проверяет обязательные согласия и действующие права; отключение identity, обязательного основания доступа или привязки может лишить покупателя услуги. Для свободных сессий, прогресса и необязательных согласий выбрать действие отдельно. course_access_starts может содержать относящийся к возврату факт начала оказания, его нельзя автоматически приравнять к позиции просмотра. |
| Заказ, оплата, акцепт и чек | Сохранить связку заказа и строк с исходным расчётом, суммы, статусы, даты, применимую версию акцепта и подлинные фискальные доказательства. Не переписывать хешированные/неизменяемые снимки и утверждённые реквизиты. Классифицировать контакт внутри обязательного документа отдельно от операционной копии. Любой перенос идентификатора должен сохранить трассировку, контроль целостности и способность подтвердить покупателя. |
| Возврат RC.2 | Приём по email в refunds.ts сверяет адрес с customer, создание исполнения читает текущий email и исходную платёжную привязку. После отправки повтор и сверка работают с замороженным конвертом, ключом и каноническим возвратом. Удаление или смена контакта до заморозки может изменить адрес чека либо сломать приём. Сохранить связанные документы, канал и минимальный контакт до закрытия необходимой цели. Сохранять незавершённый конверт на период неопределённого результата и доказательство исхода после его штатного удаления. |
| Возврат native | native-payment-refunds.ts продолжает читать customer и исходную платёжную связь при read-back. Для создания возврата нужен receiptEmail. При выпуске чека используется контакт из замороженного конверта либо текущий email как fallback. Сохранить граф order → line → request → payment/refund → fiscal event, способность читать исход и сформировать/получить чек. Исторический заказ RC.2 остаётся на первоначальной ветке исполнения. |
| LAB | Сохранить допустимый путь получить/использовать действующий билет и доказать услугу, предоплату, закрывающий чек, отмену и возврат. Удержанное доказательство показа/посещения не должно восстанавливать отозванный билет или QR. Ключи, токены и ссылки не становятся полями акта. |

**ОЖИДАЕТ E.** Для открытого обязательства выбор маршрута передачи поручения в [регламенте](README.md#5-решения-owner).
Вариант с ограниченной исходной привязкой сохраняет зависимости, выявленные в исходниках, до конкретной контрольной даты.
Правомерность остатка, возврат по каждой ветке, достаточность фискальных реквизитов и доступ после одобренного частичного
удаления требуют отдельного сквозного доказательства. Сценарий с неподтверждённой очисткой этих зависимостей запрещено
отмечать как успешно исполненный. Обязательный срок хранения по типам документов устанавливается по
[матрице](MATRIX.md), а не на основании состояния технической записи.

## Влияние на Stage A и LAB

- Для обычного FREE-сценария финансовый guard сам по себе не блокирует Stage A. G-01 по таблице начала курса
  закрыт на уровне исходников и локальных фикстур. История #291 перестала быть условием после интеграции явной
  FREE-записи в main. A-7.5 на фактической ревизии и доказательство по старой копии остаются эксплуатационными.
- Смешанный FREE + заказ, ручное право или аудит направляются оператору по [регламенту](README.md). Финансовая и
  аудиторская связи проверяются и при закрытых продажах. Отдельно отмечаются остатки у обработчиков, в копиях и
  подавление рекламы. Вывод о ветке FREE не закрывает эти критерии и не подтверждает юридический допуск.
- Профили FLEX-131 остаются перед FLEX-83 и FLEX-86 соответственно. По FLEX-8 режим восстановления с закрытой
  отправкой, поздняя отписка и сверка попыток остаются собственными критериями. D-S5 не включён в решение E.

## Локальное воспроизведение

Для каждого SHA использовать отдельное дерево с зависимостями из его lockfile. На платном кандидате применить
только diff двух тестов этой сдачи. Из репозитория со сдачей выполнить
`git diff -U1 72b02da924d342e9e2c24b2e5ce73146bdc06d77 <HEAD_СДАЧИ> -- commerce-v2/test/erasure-restore.test.ts commerce-v2/test/refunds.test.ts`
и применить вывод через git apply на дереве кандидата. Рабочий код остаётся на своём SHA.

```sh
set -e
pnpm install --frozen-lockfile
pnpm exec vitest run commerce-v2/test/{free-enrollment,erasure-restore,pd-retention,refunds}.test.ts
# На платном кандидате добавить:
pnpm exec vitest run commerce-v2/test/{native-payment-integration,native-payments,lab-lifecycle-restore}.test.ts
```

Итог: main — 104 теста в 4 файлах, кандидат — 164 теста в 7 файлах.
На main отдельно выполнен `pnpm commerce-v2:check-migrations` (37 миграций, 22 исторических дерева).
Тесты erasure проверяют локальное применение независимого подписанного журнала к старой SQLite-копии, удаление
FREE и прогресса, устойчивость подавления, точные коды, приоритет финансовой связи и полный откат при отказе.
В отдельной RC.2-фикстуре из памяти удаляются только FREE-запись другого курса и её отметка начала. Сверяются
неизменные доказательства заказа и оплаты, сохранённое право до успешного возврата, read-back по исходной
привязке и отзыв права после подтверждения. Проверка `revoked()` наблюдает состояние права в БД.
Новый вход и разрешение доступа к платному уроку входят в [отдельные сценарии профиля 1](README.md#вариант-a-и-согласование-с-313).
В native проверены отдельные операции исходной ветки, чтения
результата, формирования события чека и удержания незавершённого расчёта LAB на фальшивых адаптерах.
Это доказательства на синтетических данных. Профиль полного частичного плана с исполнителем, сквозным доступом,
доставкой чека, архивами и обработчиками — **ОЖИДАЕТ E**. Юридическая, провайдерская и эксплуатационная приёмки самостоятельны.
