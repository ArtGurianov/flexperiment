# FLEX-119 · прямой эквайринг Точки и «Точка Чеки»

Исходная ветка `codex/flex-stage3-agent-base`. База и начальный HEAD
`e67f982161114560c91de28128baec0a51a2d1b1`. Известная установленная версия Stage 2
`72b02da9`, SQLite 0037, с закрытой custody по [VPS-28](https://app.plane.so/art-workspace/browse/VPS-28/).
Эта работа проверяет исходники и изолированные фикстуры. Повторная идентификация
работающей среды требует отдельного разрешения на чтение.

## Профиль готового курса

- Commerce замораживает сумму в копейках, заказ, фискальную позицию и исполнителя.
  `paymentLinkId` — 43-символьный SHA-256 в base64url от ссылки заказа и хеша снимка
  с доменным префиксом. Точка возвращает его в операциях. При потере create-ответа
  адаптер ищет уникальное совпадение в ограниченном диапазоне страниц списка и
  затем читает подробности по `operationId`. Ссылка на оплату выдаётся после GET.
- Единственный эмитент в выбранной модели — процессор сервиса «Точка Чеки» на
  своей ККТ. Публичная оферта ООО «ЦИБ», §§2.2.1–2.3, описывает выпуск, отправку
  и фискализацию чеков оплаты и возврата процессором. Commerce передаёт одну
  позицию `full_payment / service / none` в `payments_with_receipt` и отправляет
  только команду денежного возврата исходной операции. При подтверждённой оплате
  выдаёт доступ к готовому курсу, при подтверждённом полном возврате отзывает его.
  Модель предполагает автоматический выпуск обоих чеков процессором.
  [Платёжные ссылки](https://developers.tochka.com/docs/tochka-api/opisanie-metodov/platyozhnye-ssylki) ·
  [Create Payment Operation With Receipt](https://developers.tochka.com/docs/tochka-api/api/create-payment-operation-with-receipt-acquiring-v-1-0-payments-with-receipt-post) ·
  [Оферта процессора](https://digitalkassa.ru/wp-content/uploads/2025/12/dogovor_ob_okazanii_uslug_tochka_receipt.pdf)
- Callback принимает `text/plain` JWT не больше 8 КиБ. Проверяет RS256 через
  публичный RSA JWK Точки, тип события, статус `APPROVED`, связку
  `customerCode/merchantId` и формат `operationId`. В inbox остаются хеш тела
  и минимальный идентификатор уведомления. Повтор дедуплицируется по исполнителю
  и `operationId`. Даже валидный callback запускает только чтение. Если
  `operationId` пока неизвестен Commerce, операцию догоняет sweep по
  `paymentLinkId`. [Вебхуки](https://developers.tochka.com/docs/tochka-api/opisanie-metodov/vebhuki) ·
  [acquiringInternetPayment](https://developers.tochka.com/docs/tochka-api/opisanie-metodov/vebhuki/acquiringInternetPayment)
- В денежной сверке проверяются merchant, `operationId`, эхо `paymentLinkId`,
  сумма, явная валюта при её наличии, тип CARD и факт списания. Публичная схема
  не содержит валюту в ответе. Для отсутствующего поля используется ограничение
  этого профиля на RUB, которое предстоит подтвердить на договоре.
  [Get Payment Operation Info](https://developers.tochka.com/docs/tochka-api/api/get-payment-operation-info-acquiring-v-1-0-payments-operation-id-get) ·
  [OpenAPI Точки](https://enter.tochka.com/doc/openapi/swagger.json)
- Возврат отправляется после GET исходной оплаты и проверки отсутствия прежней
  записи возврата. Используется только полный возврат. Commerce атомарно фиксирует
  границу первого POST. Ответ POST связывает дочерний `orderId` с исходным
  `operationId`. После потери ответа используется единственная полная дочерняя
  запись `Order[type=refund]`; денежный успех требует `REFUNDED` у родительской
  операции. В отсутствие гарантии банка повторных POST нет. Для такой
  атрибуции требуется исключить параллельные возвраты из кабинета или другой
  интеграции. Конкурентный полный возврат из кабинета после локального POST
  может иметь ту же сумму и тот же родительский идентификатор. Такой исход
  технически неразличим при утрате ACK. В сомнительном случае нужна
  операционная сверка.
  [Refund Payment Operation](https://developers.tochka.com/docs/tochka-api/api/refund-payment-operation-acquiring-v-1-0-payments-operation-id-refund-post)
- Фискальные события продажи и возврата создаются отдельно в `PENDING`.
  Раздельный read-back сверяет исходный платёж, дочерний возврат, вид чека,
  сумму, валюту, `FULL_PAYMENT`, фискальный признак и время выпуска. Для
  фикстуры это `GET /fixture/receipts/…`. Публичный acquiring API описывает
  денежное состояние и данные позиции, но не источник зарегистрированного чека.
  До квалификации merchant-профиля настройка `tochka` работает только
  в `local/test` с loopback-фикстурой. Commerce не отправляет команды выпуска
  чека из этого профиля.
- Commerce отказывает LAB и пакету курсов на этапе нового quote, при подтверждении
  незавершённого quote и на границе первого create, в том числе при sweep
  и `LAB=OPEN`. Уже отправленные операции и одобренные исторические возвраты
  идут по сохранённому исполнителю. RC.2 использует существующий исторический
  Refref rail. Его восстановление не открывает новый create.

## Уточнения после ревью #314 от 25.11.2026

### Восстановление до первого POST

Для Точки первый create возможен только в экземпляре checkout-запроса, который
только что записал новую операцию. Первый refund возможен только в экземпляре
исполнения, который записал новую строку возврата и получил READY от preflight.
Сохранённая строка с `dispatch_started=0` после сбоя не получает нового права
на отправку. Даже в синтетическом `COURSES=OPEN` sweep читает её без POST.
Положительный GET Точки может привязать платёж по `paymentLinkId` и снимку.
Пустой результат оставляет `CREATE_UNKNOWN`, поскольку эффект может ещё не быть виден.
Если восстановленный возврат ещё не виден или окно живого повтора истекло,
сохраняются `SUBMIT_UNKNOWN` и конверт. В аудит один раз записывается
`NATIVE_REFUND_DISPATCH_UNCERTAIN`. Если появляется возврат без доказанной принадлежности, оператор видит
`TOCHKA_REFUND_ALREADY_EXISTS`. Состояние требует сверки, исходный конверт
и родительская связь остаются доступны.

Для этих сценариев тесты сохраняют байты SQLite перед маркером, дают исходному
процессу отправить POST, восстанавливают старые байты и скрывают банковскую
операцию от первой сверки. После появления результата платёж догоняет выдачу,
а непроверенный возврат остаётся на разборе. Отдельным случаем проверяется
возврат с доказанным собственным POST и потерянным ACK. Для текущего процесса
дополнительный журнал отправок не требуется.

Внешний erasure fence сверяет независимую историю ПД, а существующий денежный
restore-CLI ориентирован на Refref. Эксплуатационный допуск native требует
независимой инвентаризации денежного хвоста, включая операции, целиком
отсутствующие в восстановленном снимке. До этой сверки рабочий контур остаётся
закрытым. Проверенные здесь контракты касаются сохранённых строк платежей и
возвратов. Модель fallback для невидимого первого POST — удержание для
операционной сверки, включая случай, когда он физически не был отправлен.

### Операционная классификация

| Наблюдение | Реакция ledger |
| --- | --- |
| Preflight REFUND готов для только что созданной строки | Один POST после записи dispatch marker |
| Preflight REFUND недоступен | Свежая строка остаётся `SUBMITTING` · `NATIVE_REFUND_PREFLIGHT_UNAVAILABLE`; живой процесс повторяет GET, из снимка выполняется чтение с сигналом оператору |
| Preflight REFUND встретил чужой или уже начатый возврат | `REVIEW_REQUIRED` · `TOCHKA_REFUND_ALREADY_EXISTS`, без присвоения чужого идентификатора |
| Разъехались реквизиты, история списания или статус | `REVIEW_REQUIRED` · отдельный код привязки, подтверждения или статуса, конверт сохранён |
| Получен негодный JSON, неполная схема или пока отсутствует запись approval | Состояние сохранено; `TOCHKA_RESPONSE_INVALID` или `TOCHKA_APPROVAL_NOT_YET_VISIBLE`; следующие чтения могут подтвердить оплату |
| HTTP/транспорт временно недоступен | Прежнее состояние и `READ_BACK_UNAVAILABLE` |
| Получено доказательство окончательного отказа конкретной попытке | `FAILED`; адаптер Точки не трактует preflight-расхождения как такой отказ |
| Найден дубликат или исчерпан бюджет поиска | `TOCHKA_PAYMENT_DUPLICATE` или `TOCHKA_PAYMENT_LOOKUP_BUDGET_EXCEEDED` в журнале операционного разбора |

Восстановление ссылки использует обе даты списка (`fromDate` и `toDate`),
ограниченные временем подготовки операции, до десяти страниц и шесть секунд
на всю цепочку. История неизвестного create читается sweep до 72 часов от стейджинга.
Затем запись уходит в `REVIEW_REQUIRED` с `TOCHKA_PAYMENT_LOOKUP_EXPIRED`.
Это эскалация, поэтому блок повторной покупки сохраняется до решения по
исходной попытке. Запрос покупателя
может ускорить один GET известной pending-операции с двухсекундным тайм-аутом
и паузой три секунды на операцию в процессе Commerce.
[Дата и список операций](https://developers.tochka.com/docs/tochka-api/opisanie-metodov/platyozhnye-ssylki)

MERCHANT-события сверяются по `executor_key` исходной оплаты даже при активной
Точке. Если исторический исполнитель отсутствует, обязательство сохраняется и
фиксируется `NATIVE_ORIGINAL_FISCAL_EXECUTOR_UNAVAILABLE`. Исторический банк и
касса fake существуют только в памяти синтетической среды. Тест передаёт их
исходные экземпляры штатному селектору и отдельно проверяет отказ обычной
композиции после переключения. Новые PROVIDER-события Точки обслуживает только
read-back чеков.

```sh
pnpm exec vitest run --project node commerce-v2/test/native-payment-{integration,contract}.test.ts commerce-v2/test/native-payments.test.ts
pnpm commerce-v2:check-migrations
pnpm exec tsc --noEmit --incremental false
pnpm test
```

## Общая ревизия после ревью

Общая база `e67f982161114560c91de28128baec0a51a2d1b1`. Порядок — [#313](https://github.com/ArtGurianov/flexperiment/pull/313)
`3f1abc954ef33ad0a0bd76e0f28b7fc5f08e6a6e`, затем delta [#314](https://github.com/ArtGurianov/flexperiment/pull/314)
`66edebe7f96502b6e2bbc070f35d05671fc24b94`. Эта пара заменила первую локальную
сборку от 24.11.2026. В актуальном FLEX-131 незавершённый платёж, возврат или
чек блокируют закрытие аккаунта. Изолированный replay уже подписанного ledger
и эксплуатационный выпуск восстановленного источника проходят через разные
точки входа. Для восстановления до финансовой сверки runtime отказывает с
`ERASURE_NATIVE_RESTORE_FINANCIAL_HOLD`.

- 0044 FLEX-131 — `57a6c94824b814d7e21f1eabd5dc352dd5e65bc9a5870b595c16602791b0daa5`.
- 0045 FLEX-119 — `11547f21822275eb5c0f958f06288ba6265f41304084d9c83d8f88e3c5a92979`.
- Отпечаток SQLite DDL для restore и retention — `f6e1eb904d862767c86ab6bf3faf838daa391456f4a3e1b9416dfd157b88f562`.

Совмещённый тест проходит на fake, HTTP-фикстуре Точки и историческом
MERCHANT-исполнителе при активной Точке. На живой синтетической копии денежный
возврат уже подтверждён, а отсутствие чека удерживает закрытие FLEX-131.
После регистрации чека операторский план допускается. В старом
зашифрованном снимке повторный replay удаляет учётные данные и сохраняет
финансовые факты. Чек возврата, который временно скрыт от снимка, остаётся
в PENDING и догоняется один раз. Первое и повторное подписанные уведомления
после удаления не восстанавливают аккаунт, прогресс, право доступа и согласия.
Сценарий с разрывом денежного хвоста проверяет, что replay не фабрикует
отсутствующий заказ. Реальные способы восстановления хвоста и эксплуатационный
допуск остаются отдельным этапом.

```sh
pnpm exec vitest run --project node commerce-v2/test/{erasure-owner,lab-showcase-upgrade}.test.ts
pnpm commerce-v2:check-migrations
pnpm exec tsc --noEmit --incremental false
pnpm test
```

Ожидание автоматического чека остаётся открытым. Через 24 часа появляется
одно событие `NATIVE_PROVIDER_RECEIPT_OVERDUE`; отсутствие исходного
исполнителя записывается отдельно. Этот порог служит сигналом для разбора.
Договорный порог устанавливается в FLEX-76. Поздно появившийся чек по-прежнему
проходит сверку.

JWK обновляется при несовпадении подписи с кэшированным ключом,
не чаще одного принудительного обновления за 30 секунд. Недоступность ключа
возвращает 503, неподлинный callback отклоняется. Денежные результаты
подтверждаются через GET.

## Второе ревью OPUS

При `TOCHKA_APPROVAL_NOT_YET_VISIBLE` или `TOCHKA_RESPONSE_INVALID` на незавершённом
платеже через час с создания платежа Commerce один раз записывает
`NATIVE_PAYMENT_READ_BACK_STALLED` для заказа. Сигнал не меняет допуск к сверке.
Позднее доказанное списание завершает оплату и выдаёт доступ.
Час — локальный технический порог, форму ответа и сроки банка уточняет FLEX-82.

Возможность повторить preflight возврата действует менее 10 минут на исходном
SQLite handle. Изолированный restore открывает новый handle. Горячая подмена
БД под работающим процессом потребовала бы отдельного барьера восстановления.
После истечения окна допуск удаляется, сохраняются конверт и
`NATIVE_REFUND_DISPATCH_UNCERTAIN`.

Draft #314 служит только для независимого ревью, его временный 0044 занят
FLEX-131 в общей сборке. Для совместной проверки порядок — #313 (0044),
#317 (0045), дельта #316 (0046 и 0047 с исходными байтами SQL).
Порядок будущего слияния подтверждает координатор в FLEX-119.
